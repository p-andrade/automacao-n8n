# 05. Glossário Técnico de Automação, n8n, IA e Versionamento

> **Navegação:** [⬅️ 04. Miniestudo Final](./04-miniestudo-final.md) | [📚 Índice da Documentação](./README.md) | [Próximo: 06. Arquitetura da Solução ➡️](./06-arquitetura-da-solucao.md)

## 📌 Visão Geral

Este glossário reúne os **22 termos técnicos fundamentais** utilizados ao longo da documentação, dos prompts e dos workflows deste projeto. Para facilitar a consulta por estudantes e iniciantes, cada conceito é apresentado em tabela com uma **definição objetiva**, um **exemplo prático** e sua **relação direta com o projeto**.

---

## 📖 Tabela de Termos Técnicos

| # | Termo | Definição Objetiva | Exemplo Prático | Relação com o Projeto |
| :---: | :--- | :--- | :--- | :--- |
| **01** | **Automação** | Execução sistemática de tarefas ou processos por meio de regras lógicas e software, reduzindo ou eliminando a intervenção manual repetitiva. | Receber dados de um formulário web, validar o e-mail e formatar o registro sem que um atendente precise copiar e colar. | É o objetivo central do desafio: planejar automações eficazes a partir de bons prompts. |
| **02** | **Workflow** | Fluxo de trabalho estruturado como um grafo direcionado de etapas (nós e conexões) que processam dados do início ao fim. | Pipeline que conecta um `Webhook` $\rightarrow$ `IF` $\rightarrow$ `Edit Fields (Set)` $\rightarrow$ `Respond to Webhook`. | Materializado nos dois arquivos `workflow.json` nas pastas `workflows/01-cadastro-de-leads/` e `workflows/02-triagem-inteligente-ia/`. |
| **03** | **Nó (Node)** | Unidade modular dentro de um workflow do n8n responsável por uma ação específica: iniciar o fluxo, transformar dados, tomar uma decisão ou chamar uma API. | O nó `Validar Dados do Lead` (`n8n-nodes-base.if`) verifica se o nome e o e-mail foram preenchidos. | Cada etapa dos nossos dois fluxos é implementada por um nó nativo documentado e ilustrado em `assets/img/`. |
| **04** | **Trigger (Gatilho)** | Tipo especial de nó que fica aguardando um evento (chamada HTTP, horário agendado, nova mensagem) para iniciar a execução do workflow. | Um `Webhook Trigger` que inicia o fluxo assim que um cliente envia um formulário de contato no site. | Ambos os workflows deste projeto iniciam com nós de gatilho do tipo `Webhook`. |
| **05** | **Webhook** | Mecanismo HTTP que permite que uma aplicação envie dados em tempo real para uma URL específica sempre que um evento acontece. | Uma requisição `POST https://seu-n8n/webhook/cadastro-leads` enviando os dados do cliente. | É a porta de entrada (`Webhook Receber Lead` e `Webhook Entrada Solicitacao`) nos dois cenários práticos. |
| **06** | **Payload** | Conjunto de dados úteis transportados no corpo (*body*) de uma requisição ou resposta HTTP, geralmente estruturado em JSON. | `{"nome": "Ana Silva", "email": "ana@empresa.com.br", "origem": "Landing Page"}`. | Exemplificado nos arquivos `exemplo-payload.json` e na pasta `exemplos/` do Workflow 02. |
| **07** | **JSON** | *JavaScript Object Notation*: formato leve de troca de dados baseado em pares `chave: valor` e listas ordenadas, legível por humanos e máquinas. | `{"status": "sucesso", "prioridade": "Alta"}`. | Formato usado tanto nos payloads de entrada/saída quanto na própria estrutura de exportação dos workflows do n8n (`workflow.json`). |
| **08** | **API** | *Application Programming Interface*: contrato de comunicação que permite que sistemas diferentes troquem informações e executem comandos de forma padronizada. | A API da OpenAI que recebe um texto e devolve uma resposta gerada pelo modelo de linguagem. | O n8n atua tanto consumindo APIs externas quanto expondo uma API própria por meio dos seus Webhooks. |
| **09** | **Endpoint** | Endereço específico (URL + método HTTP) exposto por uma API ou servidor para realizar uma operação determinada. | `POST /webhook/triagem-ia`. | Cada workflow do projeto define um endpoint exclusivo no parâmetro `path` do nó Webhook. |
| **10** | **Prompt** | Instrução textual enviada a um Modelo de Linguagem (LLM) descrevendo a tarefa, o contexto, as regras e o formato de resposta desejado. | O comando enviado ao assistente pedindo para projetar um fluxo de cadastro de leads com validação de e-mail. | É o artefato principal do desafio da DIO, entregue em [`prompts/prompt-final-desafio-dio.md`](../prompts/prompt-final-desafio-dio.md). |
| **11** | **Engenharia de Prompts** | Disciplina técnica de estruturar, refinar e validar instruções para modelos de IA a fim de obter saídas precisas, seguras e reprodutíveis. | Dividir uma instrução em Persona, Contexto, Regras de Negócio, Restrições de Sintaxe e Formato de Saída. | Detalhada no capítulo [`docs/03-engenharia-de-prompts.md`](./03-engenharia-de-prompts.md) e aplicada nos 4 arquivos da pasta `prompts/`. |
| **12** | **Agente de IA** | Componente de software que utiliza um modelo de linguagem como motor de raciocínio para analisar entradas, seguir instruções de sistema e opcionalmente acionar ferramentas. | O nó `@n8n/n8n-nodes-langchain.agent` analisando o teor de um chamado e decidindo sua categoria e prioridade. | Implementado no nó `Agente IA de Triagem` do Workflow 02 (`02-triagem-inteligente-ia`). |
| **13** | **Modelo de Linguagem (LLM)** | Rede neural treinada em grandes volumes de texto capaz de compreender contexto semântico, resumir informações e gerar texto estruturado. | Modelos como `gpt-4o-mini`, `gpt-4o` ou `gemini-2.5-flash` conectados ao n8n. | Representado pelo sub-nó `Modelo OpenAI Chat` conectado ao `Agente IA de Triagem` no Workflow 02. |
| **14** | **Credenciais** | Dados secretos de autenticação (chaves de API, tokens OAuth, senhas) armazenados de forma criptografada no n8n para acessar serviços externos. | Uma chave `sk-...` cadastrada no cofre de credenciais do n8n para autenticar chamadas à OpenAI. | Auditadas pelo nosso validador Python para garantir que nenhuma credencial real jamais seja salva dentro dos arquivos JSON do repositório. |
| **15** | **Validação** | Verificação sistemática de que os dados de entrada (ou de saída de um modelo) cumprem os requisitos de presença, tipo e formato antes de prosseguir. | Checar se o campo `email` contém `@` e se a categoria retornada pela IA pertence à lista `["Comercial", "Suporte técnico", "Financeiro", "Outros"]`. | Aplicada nos nós `IF` de ambos os fluxos, no nó `Code` do Workflow 02 e no script `tests/validar-workflows.py`. |
| **16** | **Tratamento de Erros** | Arquitetura planejada para capturar entradas inválidas, exceções ou indisponibilidades, devolvendo respostas controladas em vez de quebrar o processo. | Desviar pelo ramo `false` do nó `IF` para um nó `Respond to Webhook` que retorna HTTP `400 Bad Request` explicando qual campo faltou. | Implementado em ambos os workflows com nós dedicados de resposta de erro e lógica de fallback no Workflow 02. |
| **17** | **Versionamento** | Controle histórico das alterações feitas nos arquivos de um projeto ao longo do tempo, permitindo rastrear quem mudou o quê, quando e por quê. | Registrar a evolução dos documentos e dos arquivos `workflow.json` usando o Git. | Aplicado em todo o repositório com histórico limpo e rastreável no Git. |
| **18** | **Repositório** | Diretório central (local e/ou remoto na nuvem) onde todos os arquivos, pastas e o histórico de versões de um projeto ficam armazenados. | O repositório público hospedado no GitHub contendo `docs/`, `prompts/`, `workflows/`, `assets/` e `tests/`. | É o pacote completo entregue como portfólio para avaliação na plataforma da DIO. |
| **19** | **Commit** | Ponto de salvamento (*snapshot*) no histórico do Git que registra um conjunto lógico de alterações acompanhado de uma mensagem descritiva. | `feat: add n8n workflow examples and payloads`. | Utilizado para organizar a entrega em etapas lógicas e semânticas durante a publicação. |
| **20** | **Branch** | Linha independente de desenvolvimento dentro de um repositório Git, permitindo trabalhar em recursos ou publicar a versão estável principal. | A branch principal `main` onde reside a versão validada e pronta para produção do projeto. | Toda a entrega validada deste projeto é consolidada e publicada na branch `main`. |
| **21** | **Pull Request (PR)** | Solicitação formal em plataformas como o GitHub para revisar e mesclar (*merge*) as alterações de uma branch de trabalho na branch principal. | Abrir um PR para que outro engenheiro revise um novo workflow antes de integrá-lo à branch `main`. | Conceito essencial para colaboração em equipe ao evoluir este portfólio com novas automações. |
| **22** | **Deploy** | Processo de disponibilizar e ativar um software, workflow ou documentação em um ambiente acessível para uso real (produção ou publicação web). | Importar e ativar (`Active = true`) o workflow em um servidor n8n ou publicar o repositório final no GitHub. | Representa tanto a ativação prática dos fluxos no n8n quanto a publicação final confirmada deste projeto no GitHub. |
